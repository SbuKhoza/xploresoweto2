# XploreCMS integration contracts: Malloya Super Admin

For the future Super Admin dashboard. XploreCMS is a separate app and is **not** modified here. Everything below is a Firebase **callable** (`httpsCallable`) in region `africa-south1`, project `xploresoweto` (production) / `xploresoweto-staging`.

## Authorisation (all admin callables)
The caller must be signed in with a **verified email**, carry the `superAdmin` custom claim, **and** have an active `super-admin/{uid}` record (`role: "super_admin"`, `active: true`). All three are checked on the server on every call; a claim alone grants nothing. Failures: `unauthenticated`, `failed-precondition: email-not-verified`, or `permission-denied`. The dashboard must therefore sign in with the same Firebase project and refresh its ID token after a role change. Unknown request keys are rejected with `invalid-argument`. Every successful state change writes an `audit-log` entry (actor uid, action, ids, enumerated reason; never message or answer text).

Enums used below: **reason** = `not_useful | unsafe | duplicate | out_of_scope | incorrect | outdated | other`; **kind** = `unsupported_intent | no_match | missing_knowledge | feedback_unhelpful | feedback_correction`; **type** = `phrase_intent | answer | place_alias`; **learnable intent** = `find_restaurants, find_accommodation, find_attractions, find_activities, find_events, find_news, find_businesses, find_tours, find_tour_guides, plan_trip, build_itinerary, recommend, discover_things, ask_price, ask_hours, ask_place, find_townships, help`.

## 1. Learning candidates and statistics
* `aiAdminListLearningCandidates {status?: "new"|"approved"|"rejected" (default "new"), kind?, limit?: 1..200}` -> `{candidates: [{id, kind, signature, hintIntent, suggestedIntents:{intent:n}, count, firstDay, lastDay, status, knowledgeId?, reason?}]}`; sorted by `count`; expired candidates are never returned. `signature` is a screened, allow-listed pattern such as `find a <x> in <place>` (`<x>` unknown word, `<n>` number, `<place>` known landmark); it never contains the person's text.
* `aiAdminLearningStats {}` -> `{learning:<settings>, candidates:{total, byStatus, byKind, occurrences, top:[{kind, signature, count}], truncated}, knowledge:{total, byStatus, byType, truncated}, newCandidatesToday}`. Aggregated over at most 500 documents per collection (`truncated` says so).

## 2. Knowledge: approve, edit, reject, disable, revoke
* **Reject** / **approve** a candidate: `aiAdminReviewCandidate {candidateId, decision:"reject", reason}` or `{candidateId, decision:"approve", type:"phrase_intent"|"answer", payload}` -> `{status, knowledgeId?}`. Payloads: `phrase_intent {sigs:[1..5 signatures], intent: <learnable intent>}`; `answer {sigs:[1..5], text: 10..500 chars, no links, HTML or contact details}`. Signatures must be made only of allow-listed words and `<x> <n> <place>`; start from the candidate's `signature`. Errors: `candidate-not-found`, `already-reviewed`, `candidate-expired`, `knowledge-exists`, `signature-in-use`, `invalid-signature`, `intent-not-learnable`, `invalid-text`, `invalid-reason`, `place-alias-is-created-directly`.
* **Create directly**: `aiAdminSaveKnowledge {type, payload}`; `place_alias {alias: 4..40 lowercase letters/spaces, not ordinary vocabulary, not a built-in alias; canonical: a built-in landmark or stored township}` -> `{knowledgeId, version:1}`. Errors add `alias-too-generic`, `alias-already-built-in`, `alias-in-use`, `invalid-alias`, `unknown-canonical-place`.
* **Edit / disable / enable / revoke**: `aiAdminUpdateKnowledge {knowledgeId, action:"edit"|"disable"|"enable"|"revoke", payload?, reason?}`. `payload` (edit) holds only the fields to change and must change something; `reason` is required for `disable` and `revoke`. -> `{version, status, unchanged?}`. Each change adds a version. `revoke` is final (`revoked-is-final`): create a new item instead. A repeated disable/enable is a no-op (`unchanged:true`, no audit entry).
* `aiAdminListKnowledge {status?: "active"|"disabled"|"revoked", type?, limit?}` -> `{knowledge:[{id, type, status, version, signatures?, intent?, text?, alias?, canonical?, updatedAt}]}`.
* `aiAdminKnowledgeHistory {knowledgeId}` -> `{versions:[{version, action, reason, snapshot, at}]}`.
* Effect on Malloya: disable/revoke stops use at once on the instance that handled the call and within 60 s elsewhere. An approved `answer` appears to users as a "knowledge" block, never as verified listing data.

## 3. Learning configuration and privacy controls
Read: `aiAdminGetUsage {}` -> `{config:{enabled, limits, retention, languages, cache, retrieval, learning, luna}}`. Write: `aiAdminUpdateConfig {patch:{...}}` (deep-merged, validated, audited; an invalid patch changes nothing).
`learning`: `collect` (bool, default **false**), `privacyAcknowledged` (bool, default **false**; `collect:true` is rejected unless this is true), `use` (bool, default true; kill switch for approved knowledge), `maxNewPerDay` (1..2000, 200), `maxPerUserPerDay` (1..50, 10), `candidateRetentionDays` (1..365, 60). Unknown keys are rejected. Audit entries record the new values of these switches and numbers.
Collection checklist for the dashboard: show a blocking confirmation that the privacy notice and review are complete before setting `privacyAcknowledged`; show TTL status (see LEARNING.md); never set both flags in one click without that confirmation.
* `aiAdminPurgeLearning {scope:"expired"|"rejected"|"new"|"all", confirm?:"DELETE-ALL-CANDIDATES" (required for "all")}` -> `{deleted, more}` (400 per call; repeat while `more`). The purge and its audit entry commit together.
* User-facing, for reference: `aiSetLearningOptOut {optOut}`, `aiSubmitFeedback {conversationId, messageId, rating, correctionIntent?}`, `aiEraseMyAiData {confirm, releaseOptOut?}`, `aiGetUsage.learning`.

## 4. Luna: configuration, usage and financial safeguards (existing, unchanged)
* `aiAdminGetUsage` also returns `config.luna = {enabled, resetEpoch, limits, breaker:{failureThreshold, windowSeconds, recoverySeconds, leaseSeconds, state, blockedKind}, today:{day, tokens, calls}}`. Numbers and states only; never text.
* `aiAdminUpdateConfig {patch:{luna:{enabled?, resetEpoch?, limits?, breaker?}}}`. Limits are validated and also clamped in code to hard **ceilings** that no stored value can exceed: `dailySuccessPerUser` 10, `dailyAttemptsPerUser` 25, `maxInputTokens` 3000, `maxOutputTokens` 500, `dailyGlobalTokens` 1,500,000, `maxConcurrentPerInstance` 2, `recoveryConcurrent` 2, `timeoutMs` 8000; `dailyAttemptsPerUser >= dailySuccessPerUser`; the breaker lease must exceed the timeout. There is **no** model, provider, key or price setting: those are fixed in code / Secret Manager and cannot be set from a callable.
* Operator actions: bump `luna.resetEpoch` to clear a "blocked" breaker after fixing billing/key problems; `luna.enabled:false` is the kill switch. Users must also accept the AI Service Notice (`aiSetLunaConsent`) before any wording call.
* **Staging**: Luna is blocked at three independent layers (no secret bound in the staging manifest, environment guard, config), so `luna.enabled:true` in staging still makes no provider call. The dashboard should display that status for the staging project and must not offer a way around it.
* Financial protections that the learning work does not touch: per-user daily/burst limits (`limits`), Luna per-user and global token ceilings, the circuit breaker, idempotent request records that are never expired or erased. Erasure endpoints never delete these.

## 5. Suggested dashboard views
Candidates table (sort by count, filter by kind, expired hidden) with Approve/Reject; Knowledge table with status filter, edit, disable/enable, revoke and a version-history drawer; Statistics cards; Settings page with the `learning` block and the confirmation described above; Luna panel (read-mostly) showing breaker state and today's tokens; Purge tools behind typed confirmation.
